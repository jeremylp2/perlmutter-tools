# zome-clientside frontend build/deploy on SPIN (dev) — how genomes appear on dev

**CRITICAL BASELINE. How the Phytozome dev frontend (`phytozome-dev.jgi.doe.gov`) is built and served,
and why released genomes "disappear" from dev.** Dev runs on the **SPIN development cluster**, namespace
**`plant`**, kubeconfig `~/.kube/development.yaml` (`export KUBECONFIG=~/.kube/development.yaml` before every
kubectl — see `spin-helm-guide.md`).

## The pipeline (build → shared PVC → static server)

The frontend SPA (`zome-clientside`, React/webpack) is **not baked into an image**. It is rebuilt from the
git repo on a timer and served from a shared volume:

1. **`deploy/zome-clientsidebuilder`** (Helm release `zome-clientsidebuilder`, chart
   `zome-clientsidebuilder-0.1.0`) runs `/home/wwwzome/code/build-zome-clientside.sh` on a **supercronic
   cron every 10 minutes** (`startup.sh` writes `*/10 * * * * .../build-zome-clientside.sh`). The script:
   - builds the branch in env **`DEPLOY_BRANCH`** (fallback `master`). **Dev MUST be `trunk`.**
   - `git remote update` on the checked-out `zome-clientside`; **if remote ≠ local for that branch, it
     wipes and re-clones + `npm ci` + `npm run build`.** A fresh pod (no checkout) clones+builds on the
     first cron tick.
   - copies `zome-clientside/config/njphytozome.json` into `dist/` as **`njphytozome.json.tgz`**.
2. The builder mounts PVC **`zome-clientside-store`** at `/home/wwwzome/code/dist` (volume `html`).
3. **`deploy/zome-staticserver`** (nginx) mounts the **same PVC** at `/usr/share/nginx/html` and serves
   `njphytozome.json.tgz`. The SPA fetches + untars it **at runtime**. (A second PVC
   `zome-clientside-store-devbuild` backs the `-featurebranch`/devbuild builder + staticserver `dev-html`.)

So: **push to the tracked branch → within ≤10 min the builder rebuilds → shared PVC updated → staticserver
serves it → dev reflects it.** No image rebuild, no `current_release` change involved for the *frontend
tree* — that is separate from the `deploy_config_metadata` deploy (see below).

## Why genomes vanish from dev — DEPLOY_BRANCH drift (the 2026-09-17 incident)

Released genomes (1049/1052/1061/1064/1065) were correctly in deploy 58 (dev) + in trunk's
`njphytozome.json`, yet absent from dev. Cause: **`zome-clientsidebuilder`'s `DEPLOY_BRANCH` had been set
to a feature branch** (`feature/info-resolve-fallback`), cut from an **older trunk that predated the genome
adds** — so the builder rebuilt dev from that stale branch and dropped them. **Dev tracking anything but
`trunk` is the failure mode. Check it first.**

```bash
export KUBECONFIG=~/.kube/development.yaml
kubectl -n plant get deploy zome-clientsidebuilder \
  -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="DEPLOY_BRANCH")].value}{"\n"}'   # MUST be trunk
```

## Fix / operate

**Point dev back to trunk (immediate):**
```bash
export KUBECONFIG=~/.kube/development.yaml
kubectl -n plant set env deploy/zome-clientsidebuilder DEPLOY_BRANCH=trunk   # triggers a rollout
kubectl -n plant rollout status deploy/zome-clientsidebuilder --timeout=120s
```
**PERSISTENCE CAVEAT:** the release is Helm-managed and `helm get values` is `null` (defaults only); the
real `deployBranch` is injected at deploy time from `zome-helm-charts/zome-clientsidebuilder/
values.yaml.TEMPLATE` placeholder **`__CLIENTSIDEBUILDER_DEPLOY_BRANCH__`** (the rendered values.yaml is
NOT in the repo). So a `kubectl set env` **persists only until the next `helm upgrade`** of the release,
which re-injects the deploy-time value. To make trunk *permanent*, set that deploy-time value
(CI variable / rendered values.yaml `deployBranch`) to `trunk` in the deploy source — not just via kubectl.

**Force an immediate rebuild (skip the ≤10-min cron wait):**
```bash
export KUBECONFIG=~/.kube/development.yaml
POD=$(kubectl -n plant get pods | awk '/clientsidebuilder-/ && /Running/ && !/feature/ {print $1; exit}')
kubectl -n plant exec $POD -- sh -c 'cd /home/wwwzome/code && nohup ./build-zome-clientside.sh > /tmp/build.log 2>&1 & echo started'
# poll: tail /tmp/build.log ; npm run build takes several min (webpack).
# dist/njphytozome.json.tgz mtime updates ONLY AFTER npm run build completes, then the script copies it.
```
**Verify what dev actually serves** (staticserver, shared PVC):
```bash
SS=$(kubectl -n plant get pods | awk '/staticserver/ && /Running/{print $1; exit}')
kubectl -n plant exec $SS -- sh -c 'cd /tmp && tar xzf /usr/share/nginx/html/njphytozome.json.tgz && grep -c "<organism name>" njphytozome.json; rm -f njphytozome.json'
```
`phytozome-dev.jgi.doe.gov` itself is behind nginx basic-auth (curling it anonymously → 401); verify via
the cluster as above, not the public URL.

## Boundaries / related

- This builder only **builds+serves whatever is on the tracked branch.** The *content* of
  `config/njphytozome.json` is generated by `deploy_config_metadata`'s `update_njphytozome.sh` and
  committed to `zome-clientside` **trunk (dev)** / **production-14.0 (prod)** — see
  `deploy-config-metadata-guide.md`. Two independent things: (1) the JSON committed to the branch,
  (2) this builder rebuilding dev from that branch. Both must be right for a genome to show on dev.
- `released_in_phytozome`: **1 = dev, 2 = production** (in `deploy_config_metadata.proteome_progress`).
- Repos: `zome-clientside` (the SPA, `code.jgi.doe.gov/dsi/phytozome/zome-clientside`, dev=trunk),
  `zome-helm-charts/zome-clientsidebuilder` (the chart). Other plant deploys: `zome-proxy` (ingress/auth),
  `zome-content`, `zome-staticserver`.
- Prod frontend is a separate path (the build script has a `DEPLOY_ENV=production` branch: analytics +
  sitemap); don't assume prod uses this same dev builder/PVC.

## LOCAL dev server for fast UI iteration (no push/deploy) — built & verified 2026-09-23

Use this instead of push-to-trunk + dev rebuild for small frontend changes. Edits in
`~/git/zome-clientside` show up in the browser in **~2 s** (measured end-to-end, not from the log).

**Pieces (all local-only, listed in `~/git/zome-clientside/.git/info/exclude` — never commit):**
- `config/njphytozome_local.js` — `njphytozome.js` with `devRootUrl: ''`. Needed because the DEV
  webpack config builds ABSOLUTE API URLs (`https://phytozome-dev.jgi.doe.gov/api/...`) and the APIs send
  **no CORS headers**, so a localhost page can't call them directly. (Prod build URLs are already relative.)
- `local-dev-server.js` — webpack-dev-server 3 (HMR) that proxies `/api /hmmscore /clustergrammer /biomart
  /jbrowse` to phytozome-dev (dev API needs no basic auth) and uses `watchOptions.poll: 1000`
  (webpack's stat-polling DOES detect GPFS edits; inotify does not — see `watchers-gpfs-guide.md`).
  Binds **127.0.0.1 only** via `ZC_DEV_BIND` — do NOT use `$HOST`: NERSC sets `HOST=loginNN`, which binds
  the server to the node's network interface (exposed). Happened once; fixed.
- Launcher `$SCRATCH/zc_localdev/run_devserver.sh` (screen `zc_dev`, log `$SCRATCH/zc_localdev/devserver.log`,
  line 1 records host/PID). Runs under **Node 14.21.3** (`nvm use 14.21.3` — matches the builder image
  `node14-generic`; Node 25 is too new for webpack 4), `NODE_ENV=development NPM_ZOME=njphytozome_local
  NODE_OPTIONS=--max-old-space-size=4096`. `getMartsDataPortalListings.js` is wrapped in `timeout 45` (it can
  hang on the biomart archive fetch; falls back to cached `.martsListing.json`/`.dataPortalListing.json`).

**node_modules:** `npm ci` FAILS locally (E404) — `@dsi-phytozome/zome-react-msaview` lives in JGI GitLab's
npm registry (project 1212) and the builder authenticates with a mounted secret
(`npm ci --userconfig=/run/secrets/$WORKLOAD/dotnpmrc`). Token-free fix used: stream the builder pod's
installed tree (same commit, Node 14 ABI 83, node-sass binding linux-x64-83 works on Perlmutter glibc 2.38):
`kubectl -n plant exec <builder-pod> -- tar czf - -C /home/wwwzome/code/zome-clientside node_modules | tar xzf - -C ~/git/zome-clientside`
Verify with EXACT counts: `find node_modules -type f | wc -l` + sum of `-printf '%s'` on both sides
(2026-09-23: 116,638 files / 459,084,293 bytes / 9,414 dirs, identical). `du -sb` differs between pod ext4 and
GPFS by directory-entry sizes only — not a data gap. Re-copy only if package-lock.json changes.

**Connect from a laptop:** `ssh -L 3000:localhost:3000 -J <user>@perlmutter.nersc.gov <user>@login24`
(must be the login node running `zc_dev` — check line 1 of the log), then open `http://localhost:3000/info/508`.

**Restart:** `screen -S zc_dev -X quit; screen -dmS zc_dev bash $SCRATCH/zc_localdev/run_devserver.sh`
(first compile ~90 s; the `representative_searches.json` warning only affects home-page example searches).
**Never** `pkill -f getMartsDataPortalListings` in a command that also contains that string — it kills itself.
